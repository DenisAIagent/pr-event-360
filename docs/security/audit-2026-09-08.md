## X-01 / X-02 — XSS stockée dans le badge (ÉLEVÉE, corrigée dans le code)

**Cause** : le nom, le média et le nom d'événement d'un badge viennent du formulaire public d'accréditation (validés en longueur seulement) et étaient injectés bruts dans un `document.write`, dans une fenêtre `about:blank` qui hérite de l'origine de l'app et échappe à la CSP d'en-tête.

**Repro (avant correctif)** :
1. Soumettre une accréditation avec `lastName = X<img src=x onerror=window.__xss=1>`.
2. L'organisateur clique « Badge » (`AccreditationsTab`, X-01) ou le journaliste ouvre son badge (`SpacePage`, X-02).
3. Le script s'exécute en same-origin sur la surface concernée (le cookie de session est httpOnly, mais le cookie CSRF est lisible et `fetch(credentials:'include')` disponible).

**Cause racine** : `client/src/admin/pages/AccreditationsTab.tsx` et `client/src/public-forms/requests/SpacePage.tsx` (anciens `document.write`).
**Correctif** : encodage de sortie centralisé — `buildBadgeHtml` (pur, `@pr-event-360/core`) échappe chaque champ, pose une CSP `default-src 'none'; img-src data:` sur le document et n'émet aucun `<script>` (impression pilotée par la fenêtre ouvrante). Les deux appels passent par `client/src/lib/printBadge.ts` ; la mécanique d'ouverture est factorisée dans `printDocument.openPrintWindow` (supprime la duplication).
**Tests** : unitaire (core — échappement, absence de `<script>`, CSP, régression de la charge), intégration (en-têtes), simulation e2e (`badge-xss.spec.ts` — capture du HTML réellement écrit). RED démontré → GREEN.

### REDIS-01 — bug latent du store de rate-limit (nouveau, corrigé et déployé)

En activant Redis pour clore OPS-02, le rate-limiting s'est révélé cassé par un bug jamais exercé (Redis n'avait jamais été activé en prod) :

- **Store partagé** : un unique `sharedStore`/`authStore` était passé à tous les limiteurs → `express-rate-limit` v7 lève `ERR_ERL_STORE_REUSE`.
- **Ordre de création** : les limiteurs auth sont construits au chargement du module, avant `initRateLimitStore` → `store` y valait toujours `undefined` (Redis jamais appliqué).
- **Clés non préfixées** : deux limiteurs par IP partageaient le compteur.

**Correctif** (déployé) : chaque limiteur a un `LazyRateLimitStore` dédié, résolu à la première requête, préfixé `rl:<nom>:`. Tests : `server/test/rate-limit-store.test.ts` (préfixe distinct, pas de réutilisation, fail-open/closed). Suite serveur : 219 tests verts.

### OPS-02 — RÉSOLU

- Redis Railway provisionné ; `REDIS_URL` (référence `${{Redis.REDIS_URL}}`) puis `REQUIRE_REDIS=true` sur le service `pr-event-360`.
- Confirmation en prod : log de démarrage `[rate-limit] Redis connecté — compteurs de débit partagés entre instances.` ; l'app démarre sainement avec le garde-fou.
- **Note méthodo** : le test de monotonie de `RateLimit-Remaining` par sonde HTTP est **faussé** derrière le proxy Railway (l'IP source varie → la clé `login:<ip>:<email>` varie). La preuve retenue est le log de connexion + l'absence de log `fail-closed` (qui apparaîtrait si un `eval` Redis échouait). Ajout d'un log de connexion permanent pour l'observabilité.
